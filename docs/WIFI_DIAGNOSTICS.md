# Временная диагностика Wi-Fi

Диагностическое окружение добавляет наблюдение за Wi-Fi к текущей обычной прошивке. По сравнению с обычной сборкой той же версии сроки и условия повторного подключения, работа AP, MQTT, настройки и показания не изменяются. Алгоритм восстановления версии 3.1 описан в [README](../README.md#восстановление-wi-fi).

Она собирается только отдельной командой `pio run -e d1_mini_diag`. Сейчас это `3.1-diag-sdk305` с NON-OS SDK 3.0.5; обычная сборка — 3.1 без диагностического кода, журнала и дополнительной RAM. Первоначальное исследование выполнялось на `3.0.3-diag` со старым SDK и приложением 3.0.2; оно описано в [отчёте](WIFI_FAILURE_2026-10-24.md), после того опыта была возвращена исходная 3.0.2.

## Что записывается

- События подключения к точке доступа, отключения с числовой причиной, получения IP, таймаута DHCP и смены режима.
- Исходный статус SDK, статус Arduino, режим STA/AP, состояние DHCP, IP, политики автоматического подключения.
- Канал и BSSID из события подключения; отдельно — наличие сохранённой привязки к BSSID.
- В исторической диагностике 3.0.3 — запись `retry_begin` перед `WiFi.reconnect()` и `retry` с его результатом. В менеджере 3.1 этот вызов заменён подготовкой STA и явным `begin()`, поэтому таких записей нет; этапы видны в Serial как `[WIFI][PREPARE]`, `[WIFI][RESUME]` и `[WIFI][CONNECT]`.
- Метка запуска, время с начала запуска, свободная память, крупнейший блок, максимальная пауза основного цикла, счётчик потерянных событий.

Обработчики событий складывают небольшие записи в очередь. Файловые операции выполняются в основном цикле. Журнал не содержит SSID, паролей и cookie. Диагностика не меняет параметры радиоинтерфейса и не форматирует файловую систему.

В текущей диагностической сборке записи также выводятся в USB Serial (115200 бод), чтобы читать события при недоступном Wi-Fi. Начальная строка портала отдельно выводит пароль, как и в обычной прошивке; перед передачей USB-журнала её нужно скрыть.

## Хранение и чтение

В LittleFS находятся `/wifi-diagnostic.log` и `/wifi-diagnostic.prev.log`, до 16 КБ каждый. Записи сохраняются после перезапуска. При нехватке места или ошибке записи диагностика отключается, сохраняя работу основной программы. Состояние видно в `GET /api/status`, поле `wifi_diagnostics`.

Авторизованный `GET /api/diagnostics/wifi` возвращает оба файла в формате NDJSON. Каждая строка — отдельный JSON-объект. Пароль интерфейса остаётся прежним.

Сбор на компьютере:

```text
python scripts/capture_wifi_diagnostics.py --duration 900
```

Программа запрашивает пароль без отображения, опрашивает статус раз в 5 секунд и скачивает журнал раз в 15 секунд. После обрыва продолжает попытки чтения. Результаты находятся в `.pio/hardware/wifi-diagnostics-<время>/`; сведения с устройства дополнены временем UTC компьютера.

Если плата не восстановит связь, не выключайте её сразу. Дождитесь нескольких попыток подключения после возвращения роутера. После согласованного выключения и включения платы журнал предыдущего запуска можно скачать с восстановившегося устройства. События подключения без получения IP и повторяющиеся причины отключения позволяют различить сценарии отказа. В журнале старой диагностики дополнительно доступны пары `retry_begin`/`retry`. Сам по себе `W:--` для установления причины недостаточен.

## Возврат к обычной прошивке

Для возврата к текущей обычной версии используется `.pio/releases/WaterPressureSensor-3.1-sdk305.bin`. Именно обычная 3.1 установлена и проверена 25 октября 2026 года; диагностическая версия в этих испытаниях не собиралась и не устанавливалась. Настройки и CA при обычном обновлении сохраняются. Диагностические файлы обычная прошивка не читает.

Исторический образ до первого диагностического обновления сохранён как `.pio/hardware/firmware-3.0.2-before-wifi-diag.bin`.

Причину сбоя следует устанавливать по фактическому журналу неудачного восстановления, а не по успешной загрузке диагностической версии.
