Wemos D1 mini `wps_24728b`, адрес **http://192.168.1.68/**.

## Изменение восстановления Wi-Fi

Перед попыткой подключения текущие параметры SDK очищаются в RAM,
STA выключается и включается снова через **не менее 200 мс после завершения
выключения**. Затем явно передаются SSID и пароль из копии менеджера.
Подход основан на подготовке подключения в Tasmota; ожидание реализовано
без блокирующего `delay()`, с сохранением резервной AP и flash.

Для сохранения той же сети отдельно восстанавливается RAM перед вызовом
`begin()` с записью flash: Arduino Core может пропустить установку параметров,
если сохранённый профиль не изменился. Успех подключения требует
`WL_CONNECTED` и ненулевого IP. При длительном отсутствии связи подготовка
повторяется каждые 30 секунд.

## Автоматические проверки

Команды:

```sh
pio test -e native
pio run -e d1_mini -j 2
python scripts/verify_nonos_sdk.py
```

**154 из 154 тестов прошли** в восьми наборах, включая 16 проверок
производственного менеджера Wi-Fi с имитацией SDK:

- Граница 199/200 мс и отсчёт паузы после медленного выключения STA.
- Возврат роутера после длительного отсутствия, в том числе после закрытия AP.
- Самостоятельное восстановление SDK и новый отсчёт 30 секунд после очередного обрыва.
- Смена профиля во время ожидания, повторное сохранение того же профиля и сохранение новых параметров после ошибки SDK.
- Сохранность flash, открытая сеть, отсутствие конфигурации, ошибки отключения и смены режима.
- Статус подключения без IP, переполнение `millis()` и закрытие AP во время паузы STA.

Обычная сборка завершилась успешно. Предупреждения Python в поставляемом
`elf2bin.py` не помешали формированию BIN.

## Испытания итогового образа на плате

Повторная установка окончательного BIN и проверки выполнялись
**17:56–17:57 по Москве** через настоящий Google Chrome в headless-режиме.
Этот прогон относится к SHA-256 выше, включая исправление повторного
сохранения той же сети.

| Wi-Fi после OTA | Подключён, IP **192.168.1.68** |
| MQTT после OTA | Подключён, TLS включён |
| Датчик после OTA | Нет `fault`, `over` и устаревшего измерения |
| Настройки после OTA | Возвращаемые API значения совпали со снимком до обновления |

| Резервная AP при этих циклах | API подтвердил AP активной после восстановления STA; между циклами AP закрылась |
| MQTT после повторных подключений | Восстановился во всех трёх циклах |

Пароли API не возвращает: их сохранность проверена косвенно успешным повторным
подключением Wi-Fi, MQTT и входом в интерфейс после перезапуска.
TLS проверен с текущими настройками брокера; отдельная проверка сертификата
и всех режимов TLS в этот прогон не входила.

## Границы проверки

**Перезагрузка роутера и отсутствие сети на 1–2 минуты не проверялись:**
пользователь сообщил, что сейчас перезагрузить роутер нельзя.
Три переподключения через форму проверяют подготовку STA и применение
профиля, но не воспроизводят исходный отказ WPA после перезапуска роутера.
По этим результатам нельзя утверждать, что первоначальная проблема
окончательно устранена. Длительное наблюдение в течение двух суток
также не выполнялось.

Пауза 200 мс проверена native-тестом с управляемыми часами и кодом менеджера.
Её длительность на плате по USB Serial отдельно не измерялась: последовательный
порт во время испытаний не был доступен. Доступность резервной AP проверялась
по состоянию API, подключение к ней отдельного клиента не выполнялось.
Физическая точность датчика и калибровка этим прогоном не проверялись.
